# 总结优化进化 Skill

> 本 skill 在任务完成后执行，对照基线复盘偏差，定位根因，推动规范进化。

## 一、执行流程

```
┌─ 触发：任务完成
│
├─ 1. 收集基线
│     ├ 读取本次技术方案
│     ├ 读取相关 skill / 规范
│     └ 读取实施结果（代码 / commit / 测试）
│
├─ 2. 对照复盘
│     ├ 实际 vs 方案 diff
│     ├ 过程问题清单（bug / 返工 / 方案变更）
│     └ 输出：偏差清单
│
├─ 3. 根因分析（核心）
│     ├ 每个偏差/问题归因到 R1–R6
│     ├ 聚类：同类根因合并
│     └ 输出：根因分布
│
├─ 4. 规范体检
│     ├ 检查相关 skill 健康度
│     ├ 识别 冗余 / 过时 / 缺失
│     └ 输出：规范改进建议
│
├─ 5. 进化决策（需用户确认）
│     ├ 生成改进项清单（带优先级）
│     ├ AskUserQuestion 确认要执行的改动
│     └ 输出：确认后的动作集
│
├─ 6. 执行进化
│     ├ 更新 skill（增 / 删 / 改）
│     ├ 更新架构/方案文档
│     └ 记录变更
│
├─ 7. 记录决策
│     ├ 写一条 ADR
│     └ 更新变更日志
│
└─ 8. 输出总结报告
      ├ 本次偏差摘要
      ├ 根因分布
      ├ 进化动作
      └ 遗留待办
```

## 二、检查维度

| 维度 | 名称 | 回答的问题 |
|---|---|---|
| D1 | 方案符合度 | 实际实现和技术方案一致吗？ |
| D2 | 过程质量 | 实施中有没有反复/返工/bug？ |
| D3 | 根因归属 | 偏差/问题该归到哪一层？ |
| D4 | 规范健康度 | 现有 skill/规范本身健康吗？ |
| D5 | 进化价值 | 本次产生了哪些可沉淀的改进？ |

## 三、检查细节 Checklist

### D1 · 方案符合度
- [ ] 接口/数据结构是否一致（实际代码 vs 方案定义的 diff）
- [ ] 是否有方案外功能（实现范围 > 方案范围 = 越界）
- [ ] 是否有方案内功能未做（实现范围 < 方案范围 = 漏实现）
- [ ] 技术选型是否偏离（换了库/模式，需说明理由）

### D2 · 过程质量
- [ ] 是否出现 bug（记录 bug 类型）
- [ ] 是否反复改同一处（多次 commit 命中同文件/函数 = 返工信号）
- [ ] 是否中途改方案（方案文档有更新 = 方案不稳定）
- [ ] 耗时是否异常（远超预估 = 估算/方案问题）

### D3 · 根因归属（核心）

每个问题归到下列 **之一**：

| 根因 | 典型表现 | 动作 |
|---|---|---|
| R1 规范缺失 | 技术方案 skill 没覆盖这种情况 | 补充 skill |
| R2 规范冗余 | skill 太多导致 AI 忽略/遗忘 | 精简 / 分类 |
| R3 规范过时 | 架构已变但规范没更新 | 同步更新 |
| R4 Review 漏洞 | review skill 没拦住该问题 | 补 review 项 |
| R5 代码 bug | 规范都到位，纯实现错误 | 修代码，不改规范 |
| R6 外部因素 | 依赖/环境/第三方导致 | 记录，不一定改规范 |

### D4 · 规范健康度
- [ ] skill 总量/体积（token 占用，超阈值 = 冗余风险）
- [ ] 是否有重复内容（多个 skill 说同一件事 = 需合并）
- [ ] 是否有矛盾内容（skill A 与 skill B 冲突 = 需裁决）
- [ ] 是否分类清晰（检索成本高 = 需重组）

### D5 · 进化价值
- [ ] 是否有可沉淀改进点（根因落在 R1–R4 = 有进化价值）
- [ ] 改进点是否已落地（skill 是否已更新）
- [ ] 是否有可复用模式（解决了一个通用问题 = 可抽象为规范）

## 四、决策记录模板

每次执行进化，记录一条 ADR：

```markdown
### ADR-XXX：[本次进化主题]
- 日期：YYYY-MM-DD
- 触发任务：[bug 编号 / 需求名 / UI 名]
- 根因类别：R1–R6
- 偏差摘要：[实际 vs 方案的差异]
- 决策：[做了什么规范改动]
  - [改动 1] skill X 新增 Y 节
  - [改动 2] 删除 skill Z 中过时的 W
- 理由：[为什么这么改]
- 影响：[影响哪些后续场景]
- 回滚方式：[如何撤销]
```

## 五、抗上下文压缩机制

### 进程状态文件
在 `设计/总结优化进化/进行中/<任务名>.md` 维护进度：
```yaml
---
任务: 修复登录超时 bug
类型: bug修复
状态: 进行中
当前步骤: 3
开始时间: 2026-06-15 14:00
最后更新: 2026-06-15 15:30
---
偏差摘要: ...
待确认项: ...
```

### 检查点
每步产物单独落盘：
- `检查点/<任务名>/偏差清单.md`
- `检查点/<任务名>/根因分布.md`
- `检查点/<任务名>/确认动作集.md`

### 修改日志
追加式轨迹（不覆盖）：
```
[2026-06-15 14:20][+改动] skill X 新增 Y 节 (R1)
[2026-06-15 14:25][−回滚] 撤销上一条 (用户反馈冗余)
[2026-06-15 14:30][+重做] 新增 Y 节·精简版 (R1，合并表达)
```

### 恢复协议
压缩后按此顺序恢复：
1. 读进程状态文件 → 知道执行到第几步
2. 读检查点 → 拿回中间产物
3. 读修改日志 → 知道改了什么、是否有返工
4. 读 ADR → 知道决策依据
5. 从断点继续执行

## 六、文件存放结构

```
设计/
├── 总结优化进化 skill.md              ← skill 定义（永久）
└── 总结优化进化/                      ← 工作产物根目录
    ├── 进行中/<任务名>.md             ← 进程状态文件
    ├── 检查点/<任务名>/
    │   ├── 偏差清单.md
    │   ├── 根因分布.md
    │   └── 确认动作集.md
    ├── 修改日志/<任务名>.md           ← 追加式
    ├── 决策/ADR-XXX-<主题>.md         ← 永久
    └── CHANGELOG.md                   ← 永久
```

## 七、设计原则

| 原则 | 含义 |
|---|---|
| 最小改动 | 只改规范层真正缺失/冗余的部分，不做无关重构 |
| 分类归因 | 问题必须归类（缺失/冗余/过时/代码 bug/外部），不同类不同动作 |
| 双向治理 | 既能"补缺失"，也能"删冗余"，防止规范无限膨胀 |
| 人工把关 | 规范变更需用户确认，AI 不擅自修改基线文档 |

## 八、执行指令

当用户调用此 skill 时：

1. **确认任务信息**
   - 询问任务名称、类型（bug修复/需求开发/UI开发）
   - 创建进程状态文件

2. **收集基线**
   - 读取相关技术方案文档
   - 读取相关 skill 和规范
   - 读取实施结果（git log、代码变更）

3. **执行检查**
   - 按 D1–D5 维度逐项检查
   - 将结果写入检查点文件

4. **根因分析**
   - 将每个偏差归因到 R1–R6
   - 生成根因分布报告

5. **进化决策**
   - 生成改进项清单
   - 使用 AskUserQuestion 确认要执行的改动

6. **执行与记录**
   - 执行确认的改动
   - 写入 ADR 和 CHANGELOG

7. **输出报告**
   - 生成总结报告
   - 清理进程状态文件
